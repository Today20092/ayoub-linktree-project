# Repeatable website analytics: skill research

Researched 2026-11-06. Documentation and repository snapshots, not a live account audit. No Cloudflare settings, installations, deployments, credentials, account IDs, or beacon values were used. The public skill is a separate deliverable owned by the parent agent.

## Recommendation

Write a small new website-analytics setup skill, informed by existing measurement-planning workflows. None of the inspected candidates covers Cloudflare injection ownership, plan-dependent exclusions, sensitive routes, CSP, and proof of collection together. Prefer manual injection when route privacy must be reviewable in application code; automatic injection is also viable when its exclusion controls and actual delivered behavior are verified. **Do not claim Free plans cannot exclude routes:** Web Analytics rules have a zero quota on Free, but Configuration Rules separately offer `disable_rum` and are available on Free. [Limits](https://developers.cloudflare.com/web-analytics/limits/), [Configuration Rules](https://developers.cloudflare.com/rules/configuration-rules/), [settings](https://developers.cloudflare.com/rules/configuration-rules/settings/#disable-real-user-monitoring-rum).

The reusable workflow should discover existing instrumentation, agree on public routes, choose one injection owner, prepare the smallest change, and prove both collection and exclusion. Search Console/Bing ownership and outbound-click tracking should be optional, separate steps.

## Verified Cloudflare behavior

### Injection and exclusions

- Zone automatic setup requires proxied traffic and injects broadly, including subdomains. Manual mode measures pages where the application embeds the snippet. Select manual mode before shipping a manual embed; inspect the delivered HTML for exactly one instance. DNS-only sites require manual installation. [Setup](https://developers.cloudflare.com/web-analytics/get-started/), [FAQ](https://developers.cloudflare.com/web-analytics/faq/).
- **Web Analytics rules:** proxied sites only; Free/Pro/Business/Enterprise quotas are **0/5/20/100**. Thus “add a Web Analytics exclusion rule” is not a universal Free-plan instruction. [Limits](https://developers.cloudflare.com/web-analytics/limits/), [rules](https://developers.cloudflare.com/web-analytics/configuration-options/rules/).
- **Configuration Rules:** proxied DNS required; plan quotas are **10/25/50/300**. `disable_rum: true` turns off Web Analytics for matching requests and wins over enabling Web Analytics rules. This is a documented alternative on Free; inspect remaining capacity and actual request behavior before choosing it. It does not establish that Cloudflare can remove an application-embedded beacon or stop one already running after client navigation. [Availability](https://developers.cloudflare.com/rules/configuration-rules/#availability), [setting](https://developers.cloudflare.com/rules/configuration-rules/settings/#disable-real-user-monitoring-rum).
- **`no-transform`:** Cloudflare explicitly documents that `Cache-Control: public, no-transform` prevents automatic beacon injection. Do not add `public` to sensitive responses or remove existing privacy/cache headers to make analytics work. Origin Cache Control documentation also distinguishes enabled/disabled behavior and compression effects, so this header is not a universal, isolated analytics switch. Verify the actual response. [Setup warning](https://developers.cloudflare.com/web-analytics/get-started/), [cache-control semantics and behavior table](https://developers.cloudflare.com/cache/concepts/cache-control/).
- **Pages integration is distinct:** enabling analytics on a Pages project adds the snippet on the next deployment. Do not apply that lifecycle to an arbitrary Workers application. [Pages workflow](https://developers.cloudflare.com/pages/how-to/web-analytics/).

For a privacy-sensitive site, recommendation: explicit public-route allowlist and environment/hostname gate in the existing rendering boundary, with private/admin/gallery/upload/token-bearing routes excluded until deliberately approved. Check exact route roots as well as descendants; a prefix such as `/admin/` alone misses `/admin`. These are design recommendations, not findings about this repository's current implementation. Dashboard filtering is not collection prevention.

### CSP and navigation

Permit the external beacon in the applicable script directive while retaining existing policy. Automatic injection needs same-origin `connect-src`; manual embedding uses `https://cloudflareinsights.com`. Prefer the specific setup FAQ over the more general collection page, which describes destinations in terms of proxy status. Check the observed endpoint rather than assuming manual injection uses the proxied endpoint. Review `script-src-elem`, nonces, and `strict-dynamic` if present; do not solve this with wildcard sources or `unsafe-inline`. [CSP and endpoint guidance](https://developers.cloudflare.com/web-analytics/faq/), [collection overview](https://developers.cloudflare.com/web-analytics/data-metrics/data-origin-and-collection/).

Cloudflare documents SPA tracking through Soft Navigations, Navigation API, or History API hooks. Manual embedding supports `spa: false`. **Inference requiring testing:** withholding a script on a private route does not unload a beacon initialized on an earlier public route. For public/private client navigation, use a proven isolation strategy (for example, full document navigation across that boundary), or disable automatic SPA tracking and test the intended behavior. Response injection exclusions alone do not prove private-route collection is absent. [SPA behavior](https://developers.cloudflare.com/web-analytics/get-started/web-analytics-spa/).

### Referrals, clicks, and optional search tools

Inbound social visits can be segmented by **Referer host**; referrer path is additionally available through GraphQL. This measures visits referred to the website, not clicks leaving it for Instagram, WhatsApp, or another destination. Missing referrers should remain unknown rather than being guessed as social. [Dimensions](https://developers.cloudflare.com/web-analytics/data-metrics/dimensions/).

Cloudflare currently documents neither UTM reporting nor custom-event support. Do not promise outbound-click analytics, invent an event API, or POST custom events to its RUM endpoint. A separate, explicitly requested event-capable service or aggregate redirect measurement would be a separate scope. [FAQ](https://developers.cloudflare.com/web-analytics/faq/).

Search visibility is another separate scope: Search Console Domain properties require DNS verification, while URL-prefix properties support other methods. Prefer existing verified ownership; no browser analytics installation is needed for DNS ownership proof. Bing can import verified Search Console sites with permission, or use its independent verification methods. Prepare instructions without executing DNS/account changes in this research task. [Google ownership](https://support.google.com/webmasters/answer/9008080?hl=en), [property types](https://support.google.com/webmasters/answer/34592?hl=en), [Bing verification](https://www2.bing.com/webmasters/help/add-and-verify-site-12184f8b).

## Reproducible implementation validation workflow

The following is a proposed acceptance procedure, **not checks already performed on this website**.

1. **Inventory:** identify deployment product, existing scripts/integrations, automatic injection owners, routing mode, CSP and cache headers. With authorized read-only account access, inspect the real plan, rule capacity, analytics site hostname/mode and any existing exclusion rules. Keep identifiers and beacon values out of public notes. Do not silently create a second site or injection owner.
2. **Define a route matrix:** public homepage and public portfolio; exact private roots and nested routes; private galleries and upload/share routes; login/error pages; preview and localhost; relevant subdomains. Use synthetic paths/data. Define expected script presence and expected collection for each case.
3. **Choose and document one owner:** manual route-gated render, or automatic injection with verified available exclusions. Record the rollback (remove manual embed, or restore the prior automatic configuration). Keep private caching and authorization intact. Do not treat `no-transform` as authorization or a substitute for route policy.
4. **Local proof:** for a proposed manual embed, test route/host/environment selection, including trailing slashes and private roots. Inspect rendered HTML. Local absence cannot prove that an edge injector is disabled. Run project-required formatting and website verification for actual code changes.
5. **Delivered-response proof:** on an authorized isolated preview, inspect a full HTML GET and response headers, including final URL after redirects. Assert exactly one beacon on an allowed page and none on excluded documents; inspect CSP and `Cache-Control` on each. HEAD alone cannot prove injection. Do not record full HTML/HAR files containing identifiers or access links.
6. **Browser transport proof:** in a clean browser profile, inspect Network and Console. Load a public page, navigate, then hide/leave the tab so deferred metrics can flush. Confirm the official script loads and real beacon POSTs succeed at the expected endpoint without CSP/CORS errors. Do not use a GET probe or synthetic custom POST as ingestion proof. [Collection timing](https://developers.cloudflare.com/web-analytics/data-metrics/data-origin-and-collection/), [FAQ](https://developers.cloudflare.com/web-analytics/faq/).
7. **Privacy negative proof:** direct-load excluded pages and traverse public → private → public using client navigation, full reload, and back/forward. Observe long enough to flush lifecycle events. Assert no excluded path is present in outbound beacon payloads, including later beacons. A successful public POST proves transport, not private-route safety.
8. **Dashboard proof:** after the documented few-minute delay, select the correct site/host and narrow test time window; confirm the expected public path appears. Distinguish script delivered, POST accepted, and dashboard observed. Multiple lifecycle payloads are not automatically duplicate pageviews. Record pass/fail and timestamps without identifiers. [Setup delay](https://developers.cloudflare.com/web-analytics/get-started/).
9. **Close out:** report route-matrix results, unresolved exclusions, and rollback. If only local tests ran, explicitly leave edge injection, browser transport, and dashboard collection unverified. For real changes, production verification follows the project's separate authorized promotion process.

## Dated caveats and limits

Context7 was used for current Cloudflare setup, CSP/collection, and Configuration Rules documentation; direct official docs and upstream source files supplied citations. The research and Context7 skills were read from the requested local paths. The explicit instruction to work without subagents took precedence over the research skill's delegation default.

The reviewed Cloudflare sources describe current behavior, not the account's entitlement, existing rule allocation, or a guarantee for every Worker response. Recheck documentation before implementation. The FAQ and limits page contain different wording about site-count limits; use the dedicated limits page for planning and verify actual account capacity. Likewise, endpoint descriptions differ in specificity; validate network behavior.

Cloudflare describes Web Analytics as privacy-first; that does not make Cloudflare disappear as a service provider or establish a universal consent exemption. The new skill should describe actual collection and avoid the candidate's blanket legal claims. Referrer/URL data can still reveal sensitive paths even when query strings are omitted. Browser blockers and network loss can undercount, and edge request analytics measure a different population. No live collection, installed configuration, or compliance status was established here.

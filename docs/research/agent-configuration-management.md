# Central agent configuration management

Research date: 2026-11-03. Primary-source review only; no tools installed or configuration changed.

## Recommendation

**Rulesync is the best fit: one agent-usable, version-controlled source generates instructions, MCP settings, and skills for Claude Code, Codex, DeepSeek Harness and Grok CLI.** A GUI is not required. CC Switch is a secondary option if visual management becomes useful. These solve configuration distribution; neither claim should be read as automatic communication between independent running agents.

The user confirmed **DeepSeek Harness**; it is distinct from **LangChain deepagents-cli**. “Grok” still needs to match the actual executable: **Grok Build**, a third-party **Grok CLI**, or a Grok model inside another application are not interchangeable adapter identities. Rulesync lists both DeepSeek Harness and deepagents-cli; CC Switch's README explicitly lists Grok Build but does not list either DeepSeek Harness or deepagents-cli in its supported-tool list. [Rulesync README](https://github.com/dyoshikawa/rulesync#readme), [CC Switch README](https://github.com/farion1231/cc-switch#readme).

## Practical choice

For a graphical hub, evaluate **CC Switch first** with a small set of shared MCP servers and skills. Its prompt editor preserves the previous instruction file in the library when activating another prompt. It also supports custom configuration directories and device synchronization, but that does not establish support for every harness or every plugin format. Its provider-routing features are separate from configuration synchronization and are unnecessary for this use case. [CC Switch documentation](https://github.com/farion1231/cc-switch#readme).

For exact cross-harness coverage, evaluate **Rulesync first**, confirming that its Grok adapter matches the installed Grok harness. Its support matrix distinguishes native features, global scope, and settings. Codex command support, for example, is scope-specific. Choose only the desired targets/features, import existing settings, and inspect generated diffs before adopting the generated files as managed outputs. [Rulesync supported tools](https://rulesync.dyoshikawa.com/reference/supported-tools.html).

The important DeepSeek Harness limit is **MCP generation is global-only**; rules and skills support project and global scope. Its adapter does not claim hooks, permissions or subagents. Thus a single canonical source can cover the requested core configuration, but cannot provide identical project-scoped behavior for every component. [Rulesync support matrix](https://rulesync.dyoshikawa.com/reference/supported-tools).

Rulesync is suited to agent-operated maintenance: the CLI provides JSON output, dry runs, watch mode, a read-only doctor, and `generate --check` to detect drift with a failing exit status. These provide a concrete review/check workflow around the central source. [Rulesync CLI reference](https://rulesync.dyoshikawa.com/reference/cli-commands).

It also provides its own MCP server so an agent can manage shared rules, skills and MCP definitions, import existing configuration, run generation, and diagnose configuration through tool calls. Its generation tool supports preview and drift checks; for MCP checks the agent must read the returned `upToDate` field rather than expect a failing CLI exit code. This is especially relevant when the manager itself should be operated by an agent. [Rulesync MCP server](https://rulesync.dyoshikawa.com/reference/mcp-server).

Plugins require special treatment. Rulesync can generate components inside certain plugin layouts, including Claude Code plugins, but generally does not create manifests, marketplace catalogs, scripts or other package assets. There is no evidence here of a lossless conversion of all installed plugins between Codex, Claude, DeepSeek/deepagents and Grok. [Rulesync plugin packaging](https://rulesync.dyoshikawa.com/guide/plugin-packaging.html).

Do not give two managers ownership of the same generated instruction/MCP/skills files. That recommendation is an operational inference: each manager writes native configuration, so overlapping ownership can replace another manager's output. Paths and credentials remain machine-specific; a portable source must preserve environment references rather than committing secrets.

## Other candidates and verification limits

[Microsoft APM](https://github.com/microsoft/apm) is worth revisiting if the main need becomes reproducible package/plugin dependencies with a manifest and lockfile. It is MIT and publishes Windows binaries. Its current README names Grok Build, but the illustrated MCP installation target list omits Grok, and it does not establish the required DeepSeek/deepagents coverage. It is therefore not the first recommendation for this particular set. [APM README](https://github.com/microsoft/apm#readme), [APM license](https://github.com/microsoft/apm/blob/main/LICENSE).

An indexed result describes `Jonathangadeaharder/agentalign`, but its repository and raw README returned 404 during this review; its current availability, license and support could not be confirmed. No uniquely identified “Manifest” configuration project was established, so that name is not treated as a verified candidate.

This review did not install software, test native Windows synchronization, compare released binaries against main-branch documentation, or validate preservation of existing local settings. Documentation claims should be checked against the chosen release before migration. Free/open-source manager software does not make the agents' model/API usage free.
